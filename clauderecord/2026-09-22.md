#### V1.10.0 - 2026-09-22
- **修改类型**：新增（飞特 Feetech SCS 总线舵机驱动包移植）
- **涉及模块**：硬件驱动层 / 新增 `hardware/actuators/scslib/`（厂商库 11 文件）与
  `hardware/actuators/servo_scs.c`、`hardware/actuators/servo_scs.h`（工程胶水层）；

- **修改内容**：
  1. **收编厂商库**：`D:\Downloads\FTServo_stm32HAL-main\...\SCSLib\` 的 11 个文件原样迁入
     `hardware/actuators/scslib/`，**协议代码一行未改**，只做编码归一 —— 源包是
     **混合编码**（`HLS` / `SCSCL` / `SMS_STS` 六文件为 UTF-8，`SCS.c/h` / `SCSerail.c` /
     `INST.h` / `SCServo.h` 五文件为 GBK），已全部转为 UTF-8。
     未做归一的话，GBK 第二字节可能是 `0x5C`（`\`），落在 `//` 行尾会触发续行，是个隐蔽坑。
  2. **实现唯一接缝**：厂商把硬件接口抽象成三个函数
     （`ftUart_Send` / `ftUart_Read` / `ftBus_Delay`），**只在 `scslib/SCSerail.c` 里声明、
     全包内无定义** —— 厂商 README 第 5 条「根据自己定义的串口修改 ftUart_Send/ftUart_Read」
     说的就是这件事。三个函数的实现落在 `servo_scs.c`，接的是 **UART5（PC12=TX / PD2=RX）**，
     波特率 1 M。厂商 11 个文件因此可以保持与上游逐字节可比，便于日后升级。
  3. **波特率在运行期改写，不动 CubeMX 生成区**：`SCS_BusInit()` 把
     `huart5.Init.BaudRate` 置为 `SCS_UART_BAUD` 后重调 `HAL_UART_Init()`。
     `HAL_UART_Init()` 在 `gState != RESET` 时**不重跑 MspInit**，只重算 BRR，
     因此不会重配 GPIO / 时钟 / NVIC，是安全的原地改速率。这样 `Core/Src/usart.c`
     里那行生成态 `huart5.Init.BaudRate = 115200;` 不必手改。
     PCLK1 = 170 MHz，过采样 16 → BRR = 170，整除、零误差。
  4. **互斥保护**：`servo_scs.c` 提供 `SCS_Lock()` / `SCS_Unlock()` 与 20 个 `SCS_*` 包装
     函数（三套系列的位置/速度/使能/回读核心命令），每个包装都是「取锁 → 调厂商函数 → 放锁」。
     **这是本工程第一次使用 `osMutex`** —— 此前全工程零互斥量，共享外设一律靠
     「单任务调用 + volatile 标志」约定。厂商 API 本身是「发一帧→收一帧」的时序，
     两个任务并发调用会让总线字节交错、双方都失败，故这里必须串行化。
     取锁失败（未初始化 / 非任务上下文 / 超时）时**降级为无锁执行**并累加诊断量
     `g_scs_mutex_timeout`，而不是让舵机命令整条发不出去。
  5. **RTOS 安全的两处防御**（照 V1.6.2 的教训）：
     - `ftBus_Delay()` 在调度器未启动时走 `HAL_Delay()` 而非 `osDelay()` ——
       `osDelay()` 在调度器启动前调 `prvAddCurrentTaskToDelayedList` 会 NULL 解引用跳 HardFault；
     - `SCS_Lock()` 在 `osKernelGetState() != osKernelRunning` 时直接返回「未持锁」，
       不让 `osMutexAcquire` 走进阻塞路径。
     互斥锁的**创建**（`osMutexNew`）不受此限，FreeRTOS 堆是静态数组，可无条件建。
  6. **CMake**：`target_include_directories` 增加 `hardware/actuators/scslib`。
     源码无需改 glob —— `hardware/*.c` 是 `GLOB_RECURSE`，新子目录自动收集。
  7. **诊断量**：`g_scs_uart_tx_err` / `g_scs_uart_rx_err` / `g_scs_mutex_timeout`
     （声明在 `servo_scs.h`），照 `Core/Src/can.c` 的 `can_error_step` 模式。
- **影响范围**：**仅新增，既有代码零改动**。业务层与其它驱动不受影响，`active_locator`
  等待接入的模块也不涉及。UART5 此前虽已初始化但**全工程零调用**，本驱动是它的首个使用者；
  UART4 仍空闲。舵机命令目前**尚未被任何任务调用**，故 `SCS_BusInit()` 也还没被接线。

- **备注**：
  1. **兼容升级**：纯新增，未修改任何已有接口、结构体或构建产物。
  2. **【既有隐患，本次未修】`.ioc` 里 UART5 不受 CubeMX 管理**。`bydcar_g491vet6.ioc`
     有 `Mcu.IP10=UART5` 与 PC12/PD2 的引脚分配，但**唯独缺 `UART5.IPParameters=` 属性行**
     —— 对照 `USART1/2/3` 三行的写法：
     ```
     USART1.IPParameters=VirtualMode-Asynchronous
     USART1.VirtualMode-Asynchronous=VM_ASYNC
     ```
     且 `.mxproject` 中 grep `UART4|UART5` **零命中**。说明这两个串口是**手工塞进 .ioc 的**，
     CubeMX 并未真正当作受管外设。**若重新生成工程，`MX_UART5_Init()` 有被整段删除的风险**，
     届时 `SCS_BusInit()` 会因 `huart5.Instance == NULL` 返回 0（**优雅失败，不会崩**），
     但舵机将完全不能通信。**建议在 CubeMX GUI 里把 UART5 正式勾选并设为 1M 后重新生成**，
     由 CubeMX 自己写出那两行属性；不建议手改 .ioc。UART4 同样是这个状态。
  3. **本驱动用阻塞式收发，与工程其它串口驱动（一律走 IT / DMA）不同**，这是有意的：
     厂商协议是严格「发一帧→收一帧」时序，阻塞实现最简单也最易验证。
     代价是**舵机不应答时每字节耗时 `SCS_UART_RX_TIMEOUT_MS`（默认 100 ms）**
     —— 协议层 `checkHead()` 读首字节超时即返回。故本驱动只应在**低频命令任务**里调用，
     **不要放进控制环**。若 100 ms 的失败代价太大，调 `servo_scs.h` 的该宏即可。
  4. **厂商 `rFlushSCS()` 只是 `ftBus_Delay()`，并不真正清空接收 FIFO**。它的名字
     （接收缓冲区刷新）与实现不符。若总线上残留上一帧的字节，会被下一条命令当成应答读走，
     表现为偶发校验错。真出这类问题时，应在 `ftBus_Delay()` 里补一次 RX 清空
     （`__HAL_UART_CLEAR_OREFLAG` + 读空 DR），或改用带 ID 校验的重试。
  5. **厂商的 `syncReadBegin()` 用 `malloc`**。工程 `.ld` 的 `_Min_Heap_Size = 0x200`，
     `_sbrk` 定义在 `Core/Src/sysmem.c:53`，堆实际从 `_end` 长到 `_estack - _Min_Stack_Size`，
     容量充足（`syncReadBegin(IDN, rxLen)` 只申请 `IDN*(rxLen+6)` 字节）。
     但该函数当前被 `--gc-sections` 回收，**要用同步读就得先真正调用它**。
  6. **厂商 API 命名过于通用**（`Read` / `Reset` / `Ping` / `writeByte` / `checkHead` /
     `wBuf` …）。本次经 `nm -u` 确认**与工程现有符号无冲突**，但这些名字迟早会撞上
     新代码，届时报错点在链接期、很好定位。若要预防，可在 `scslib/` 外统一加前缀，
     但那会破坏与上游的可比性，故本次保留原名。
  7. **未做的接线**：`SCS_BusInit()` 需要在任务里调用一次（建议放在现有 Worker 任务
     启动处，与 `HWT_IMU_Init()` 同级）；舵机 ID、角度范围、以及是否用
     `SyncWritePos` 组帧，都取决于实车机械结构，待用户明确后再接。

#### V1.10.1 - 2026-09-22
- **修改类型**：新增（按确定的舵机型号 STS3032 补全包装与文档）
- **涉及模块**：硬件驱动层 / `hardware/actuators/servo_scs.c`、`hardware/actuators/servo_scs.h`
- **修改内容**：用户确认目标舵机为 **STS3032**，属厂商的 **SMS_STS 系列**。三套系列
  （SCSCL / SMS_STS / HLS）在 V1.10.0 已全量移植，故本次**无需增删任何文件**，
  只补齐 SMS_STS 系列实际要用的包装与前置文档：
  1. **补 EPROM 解锁包装对** `SCS_UnlockEprom()` / `SCS_LockEprom()`
     （转调 SMS_STS 的 `unLockEpromEx` / `LockEpromEx`）。**这是改 ID / 模式 /
     角度限位的前置条件** —— 这些寄存器在 EPROM 区，未解锁写入不生效且**不报任何错**。
     V1.10.0 漏掉了这两个，等于「能发位置但改不了配置」，用起来会卡住。
  2. **补 10 个包装**：`SCS_RegWritePosEx`、`SCS_SyncWriteSpe`、
     状态回读五个（`SCS_ReadSpeed` / `ReadLoad` / `ReadVoltage` / `ReadTemper` /
     `ReadCurrent`）、以及 `SCS_GetLastError()`（读 `SCS.c` 静态量，**刻意不加锁** ——
     加锁反而会读到别的任务刚覆盖的值）。包装总数 20 → 35。
  3. **`SCS_BusInit()` 补 `setEnd(0)`**：显式钉住小端字节序。厂商每个 SMS_STS 例程
     的 `setup()` 都调它；`SCS.c` 里 `End` 初值本来就是 0，故当前是**幂等的空操作**，
     写出来是为防止将来有人改 `SCS.c` 初值导致 STS 系列字节序静默反转。
  4. **头文件补两条前置警告**：①调用任务**至少 1 KB 栈余量**（厂商 `SyncWritePosEx` /
     `SyncWriteSpe` 各在栈上开 `uint8_t offbuf[32*7]` = 224 字节，见 `SMS_STS.c:47`、`:116`，
     而 `gripper` 任务当前只有 512 字节）；②`SCS_WritePosEx` 内部一次写地址 41~47
     共 7 字节，`position` 为 **0~4095 对应 0~360°、中位 2048**，`speed` / `acc`
     是**原始寄存器值**（单位随型号，以数据手册为准）。
- **影响范围**：仅新增包装与注释，**未改动任何既有接口或厂商库代码**。
  `scslib/` 下 11 个文件仍与上游逐字节可比。包装函数仍是 0 调用者，
  整段被 `--gc-sections` 回收，对 FLASH / RAM 占用无影响。

  1. `cmake --build --preset Debug --clean-first` 全量重编，**0 error、0 新增 warning**；

  2. `nm` 确认 `servo_scs.c.obj` 内 `SCS_*` 强符号由 20 个增至 **35 个**，
     新增的 `SCS_UnlockEprom` / `SCS_LockEprom` / `SCS_RegWritePosEx` / `SCS_SyncWriteSpe` /
     `SCS_ReadSpeed` / `SCS_ReadLoad` / `SCS_ReadVoltage` / `SCS_ReadTemper` /

- **备注**：
  1. **兼容升级**：纯新增。
  2. **【发现厂商例程 bug，本次未改厂商库】`examples/SMS_STS/ProgramEprom.c` 是错的。**
     它调的是 **SCSCL 系列**的 `unLockEprom(1)` / `LockEprom(2)` —— 而 SCSCL 的锁寄存器
     在地址 **48**（`SCSCL.h:36`），SMS/STS 的在地址 **55**（`SMS_STS.h:40`），
     两者不可混用；且它解锁 ID 1 却锁定 ID 2，ID 也不配对。
     照抄这个例程去改 STS3032 的 ID 会**毫无效果且无报错**。
     正确做法是用 `SCS_UnlockEprom(id)` → 写 → `SCS_LockEprom(id)`。
  3. **`SCS_SetMode()` / `SCS_WheelMode()` 内部不解锁 EPROM。** 二者都是裸
     `writeByte(ID, SMS_STS_MODE=33, …)`（`SMS_STS.c:79`、`:84`），而 MODE 属 EPROM 区。
     故**切换位置/恒速模式必须自己先解锁**：
     `SCS_UnlockEprom(id)` → `SCS_SetMode(id, 1)` → `SCS_LockEprom(id)`。
     这条在厂商文档里没有明说，是照寄存器表推出来的，**待实机确认**。
  4. **状态回读函数的实现在 `scslib/SCSCL.c` 而非 `SMS_STS.c`** —— 因为 SMS/STS 与
     SCS/CL 共用同一张内存表（`PRESENT_SPEED_L` 等地址完全一致），厂商让 STS 系列
     复用了 SCSCL 的实现。这不是笔误，已在源码里注明，**不要「修正」到 SMS_STS.c**。
  5. **`setEnd(0)` 与 `End` 初值**：`SCS.c:13` 的初值就是 0（小端），与 SMS_STS 要求一致，
     故本次未产生行为变化。
  6. 待接线项同 V1.10.0 备注 7：`SCS_BusInit()` 尚未被任何任务调用；`gripper` 任务
     栈建议从 512 提到 2048（改 `.ioc`）。
  7. **【本次自查发现的 API 缺陷，已修】回读函数的 `id` 必须是 `int`，不能用 `uint8_t`。**
     厂商用 **`ID == -1`** 表示「从 `FeedBack()` 填好的静态 `Mem[]` 缓冲区取，
     **不再上总线**」（实现见 `scslib/SCSCL.c` 的 `ReadPos` / `ReadSpeed` / `ReadLoad` /
     `ReadVoltage` / `ReadTemper` / `ReadMove` / `ReadCurrent`，全部是
     `if(ID==-1){ 取缓冲区 } else { 走 readWord(总线) }` 的二分）。
     V1.10.1 初稿把 `SCS_ReadPos` / `SCS_ReadMove` 声明成了 `uint8_t id`，
     传 -1 会被截成 **255**，等于去访问一个不存在的 ID 255 ——
     静默失去「一次往返取全部状态」的能力。已改为 `int`。
     **正确用法**：`SCS_FeedBack(id)` 一次总线往返取回 7 个量，
     随后 `SCS_ReadPos(-1)` / `ReadSpeed(-1)` / … 全部零延时从缓冲区取。
     `SCS_FeedBack` 本身也刻意用 `int`，且头文件里加了 `@warning` 说明。

#### V1.10.2 - 2026-09-22
- **修改类型**：新增（应用层接线：`gripper_task` 接上舵机总线自检）＋ 修复（三处配置缺陷）
- **涉及模块**：应用层 / `Core/Src/app_freertos.c`；配置 / `bydcar_g491vet6.ioc`、
  `Core/Inc/FreeRTOSConfig.h`
- **修改内容**：
  1. **`gripper_task` 接上舵机**：启动时 `SCS_BusInit()` → 扫描 ID 1~6 →
     `SCS_FeedBack()` 一次往返取回位置/速度/电压/温度并打印 → 发一个中位命令 →
     进入 500ms 循环持续回读。串口输出走 `huart2`（PA2/PA3, 115200）。
     这一步的目的是**确认「供电 / 接线 / 波特率 / 舵机 ID」四件事是否都对**，
     真正的抓取动作待机械结构定了再接。
  2. **【修复】修掉一处 printf 实参缺陷**：初稿写成
     `printf("STS3032 id=%u online\r\n", id, SCS_ReadPos(id));` ——
     格式串只有一个 `%u` 却传了两个实参，**位置值被静默丢弃**，永远打不出来。
     已改为走 `SCS_FeedBack(id)` + `SCS_ReadXxx(-1)`，一次总线往返取回四个量
     （比逐个 `SCS_ReadXxx(id)` 省 3 次往返）。同时把 `uint8_t` 实参统一
     `(unsigned)` 强转，避免 `-Wformat` 的类型不匹配。
  3. **【修复】`#define` 移出生成区**：初稿把 `STS_ID` / `STS_CENTER` / `STS_SPEED` /
     `STS_ACC` 放在 `USER CODE END Header_gripper_task` 与函数签名之间 ——
     那一段属 **CubeMX 生成区**，重新生成会**静默删除**。已移入
     `/* USER CODE BEGIN PD */` 区，并加注释说明原因。新增 `STS_SCAN_MAX_ID`。
  4. **【修复】`configCHECK_FOR_STACK_OVERFLOW` 此前完全未定义。**
     CLAUDE.md V1.6.2 记「已设为 2 并实现 `vApplicationStackOverflowHook`」，
     但当前 `Core/Inc/FreeRTOSConfig.h` 里**根本没有这个宏**（默认 0，完全静默），
     于是 `app_freertos.c` 里的 `vApplicationStackOverflowHook()` 一直是**死代码**
     —— 这**正是 V1.6.3 备注 3 预言过的「CubeMX 重新生成会冲掉」**，只是当时没人回头核对。
     现恢复为 `2`（上下文切换时校验栈尾 0xA5 图案），并加了醒目注释。
  5. **`gripper` 任务栈 512 B → 2048 B**。512 B 放不下 `printf`
     （newlib `vfprintf` 要数百字节），也扛不住厂商 `SyncWritePosEx` 在栈上开的
     224 B `offbuf`（`servo_scs.h` 的 `@warning` 记过）。改在**两处并保持一致**：
     `.ioc` 的 `FREERTOS.Tasks01`（`gripper,24,128` → `gripper,24,512`，单位是**字**）
     与 `app_freertos.c` 的 `gripper_attributes`（`128*4` → `512*4`，单位是**字节**）。
  6. **`configTOTAL_HEAP_SIZE` 8096 → 16384**，同样两处同改
     （`.ioc` 的 `FREERTOS.configTOTAL_HEAP_SIZE` 与 `FreeRTOSConfig.h`）。
     不改的话，栈提到 2048 后栈总量 6656 B + 5×TCB + 队列 ≈ 7400 B 会几乎吃满 8096 B，
     而 `osThreadNew()` / `osMutexNew()` 在堆耗尽时**返回 NULL 且不报错**（V1.4.0 先例），

  2. **【动机】与厂商参考实现的逐项对比结论。** 对比
     `D:\Downloads\FTServo_stm32HAL-main\FTServo_stm32HAL-main\Core\Src\main.c`
     与 `SCSLib/`（本工程 `scslib/` 即由此逐字节搬入）：

     而厂商 demo 与能正常驱动这套舵机的 FD 上位机都工作在「TE 常开」的等价条件下。
  3. **【原理】为什么原来的理由不成立。** 原注释的理由是「不清 TE 的话 PC12
     空闲时被 push-pull 强驱动高电平，舵机回包拉不低这条线」。该理由成立的
     前提是**单线半双工** —— PC12 与 PD2 并接到同一根信号线。实机
     `SCS_PinTieTest()` 在使用**总线舵机驱动板**时稳定返回 `1/2`
     （`pintie` 表示「PC12 拉低/拉高，PD2 各读到几次」，2 才是连通）：
     PC12 的驱动传不到 PD2，说明板子把 TX/RX 分成了两路，前提不成立。
     更强的反证：能正常驱动这套舵机的 FD 上位机走的是 USB-TTL，
     **USB-TTL 的 TX 本就是永久 push-pull 空闲高**，与「TE 常开」等价；
     硬件既然吃得消那种接法，清 TE 就只剩代价。
  4. **【代价】TE 由 0 置 1 会先发一个 idle 帧。** ST 参考手册明确：
     「the USART sends an idle frame before the first data frame」。
     原实现除第一帧外每帧都翻转一次 TE，等于每帧前都可能多出一段额外发送。
     至于该 idle 帧是否会被舵机解成一个多余字节（进而把 `FF FF` 帧头挤错位），
     **尚未用逻辑分析仪确认**，本次不据此下结论。
  5. **【为什么必须成对改】只注释掉 `SET_BIT(TE)` 而留下 `CLEAR_BIT(TE)`
     是一个更坏的状态**：第一帧发完 TE 就永久为 0，此后数据写进 TDR 也移位
     不出去，`HAL_UART_Transmit()` 会等满超时，表现为 `tx_err` 暴涨、总线全哑。
     本次三处 TE 操作一并清除，并在 `ftUart_Send()` 上加了 `@warning` 防止回退。
  6. **【仍未修】本次只做了用户要求的「对齐厂商实现」，两个已定位的缺陷未动**：
     ① `SCS_LoopbackTest()` 的 `if (guard == 0) break;` 恒为假 —— 后置自减在
     超时退出时把 `guard` 从 0 减到 `0xFFFFFFFF`，导致早退失效，且超时后仍会
     读陈旧的 `RDR` 参与比对；② `SCS_PinTieTest()` 只返回 `low_ok + high_ok`，
     丢掉了「哪个方向没读到」，而两个方向对应完全相反的故障（被强上拉 vs 被强下拉）。
  7. **【仍未查】`FE=1` 的来源未定论。** `ISR=0x004200D2` 解出 bit1 FE=1、
     bit4 IDLE=1。但 `HAL_UART_Init()` 不清错误标志
     （核过 `stm32g4xx_hal_uart.c:307-374`，全程无 `__HAL_UART_CLEAR_FLAG`），
     且 PD2 在 `MX_UART5_Init()` 之前是悬空脚，因此 FE 可能是上电残留、
     可能是驱动板换向毛刺、也可能是波特率问题 —— 三者含义完全不同。
     要定性，需在自检开始前先主动清一次标志。故 `gripper_task` 里那句
     「ORE/FE/NE 有置位=线有电平但采样不对」的判读**结论过于自信**，暂按待定处理。

  特别是 V1.10.5 的广播动作验证：`rx_err` 只能说明「收不到」，分不开
  「舵机没收到所以没回」与「舵机回了但回包没到」；正是「舵机一动不动」
  这个**外部可观测事实**把范围从整个系统收缩到了发送路径那一段。

  **【遗留观察，未定性】`pos=8` 与固件命令的位置不符。** 代码在自检中先后写入
  2048（点名）、1848 与 2048（广播），而舵机报告 `pos=8`。
  且 `spd=0`、`load=0`、`cur=0` —— 不是「被憋住」，而是**根本没在尝试移动**，
  故怀疑位置写指令未被舵机接受。下一步建议用厂商 FD 上位机直接读该舵机的
  寄存器（重点看 `SMS_STS_TORQUE_ENABLE`(40) 与 `SMS_STS_MODE`(33)），
  或核对型号是否确实属 SMS_STS 系列（寄存器起始地址 41 是 SMS_STS 专用；
  若实为 SCSCL 系列，写到 41 会落到别的寄存器上）。
- **备注**：
  1. **兼容升级**：纯新增调试代码，关掉 `SCS_TX_TEST` 即完全消除副作用。
  2. **【为什么非它不可】`rx_err` 分不开两种原因。** `rx_err=1` 只能证明
     「MCU 收不到东西」，但收不到有两种成因：(i) 舵机根本没收到有效帧所以没回；
     (ii) 舵机回了但回包没到 MCU。这两者从 MCU 侧读任何寄存器都区分不了
     —— `SCS_BusSnapshot()` 看到的只是 PD2 的静态电平与错误标志。
     只有让舵机**动起来**，才能从外部观察「发送到底成没成功」。
     这是在无法接示波器/万用表时唯一还能推进的观测手段。
  3. **【关键：广播写不应答】** 协议层 `Ack()` 对 `ID == 0xFE` 直接返回 1、
     不读应答（`scslib/SCS.c:449` 的 `if(ID!=0xfe && Level)`）。所以舵机不应答时
     广播写**既不阻塞也不报错** —— 串口上不会有任何失败提示，`SCS_GetLastError()`
     也不会有值。判定完全依赖肉眼观察舵机，不要去看串口。
  4. **【安全】已经过用户确认。** 本次改动会让机械真的动作，实现前已明确征询并
     获得同意。`SCS_TX_TEST_OFFSET` 取 200 刻度（≈17.6°）是有意保守：
     够肉眼看见，又不至于撞硬限位。速度给 150、加速度给 20 也都是为了让起步缓。
     若机械上有限位或夹持，把 `SCS_TX_TEST` 置 0。
  5. **【若舵机没动，下一步就明确了】** 那说明发送路径本身就是断的，
     接收侧（PD2、板子的回包通路、`rx_err`）**全部不用再查**，
     排查范围直接收缩到 `PC12 → 驱动板 → 总线` 这一段。

     或 `MIN/MAX_ANGLE_LIMIT`(9~12) 被设窄。

     说明写指令本来就是好的；若纹丝不动，就去查上面三个寄存器。
