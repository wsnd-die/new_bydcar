#### V1.10.7 - 2026-09-23
- **修改类型**：修复（总线字节序错误 / 参数取值错误）
- **涉及模块**：硬件驱动层 / `hardware/actuators/servo_scs.c`、`servo_scs.h`；
  应用层 / `Core/Src/app_freertos.c`（仅常量与注释）
- **修改内容**：

  1. **根因：SCS0009 的字节序反了。** 飞特官方《通信协议高低字节问题》原文
     「协议中：SCS 系列高字节在前，SMS/STS 低字节在前」。厂商库不会自动区分 ——
     字节序是一个进程级全局量 `End`，只由 `setEnd()` 切换，在 `scslib/SCS.c:50`
     的 `Host2SCS()` / `SCS2Host()` 里生效。本工程此前只在 `SCS_BusInit()` 里
     调了一次 `setEnd(0)`（小端），**对 ID1 的 STS3032 正确，对 ID2~6 的
     SCS0009 全错**。

     后果：`SCS_WritePos()` 把位置的低字节放在地址 42、高字节放在 43
     （`scslib/SCSCL.c:14-21`），而 SCS0009 期望 42 是高字节。于是舵机收到的
     目标位置恒等于 `发送值 << 8`：发 1 实际是 256，发 2 是 512，发 3 是 768，
     发 4 是 1024。按 0.293°/步换算，**每 +1 就固定多转约 75°** ——
     这正是「发 0,1,2,3,4 会固定旋转一个角度」的来源。

  2. **修复方式：按系列在锁内切换字节序。** 本工程一条 UART5 上同时挂了两个
     字节序相反的系列，而厂商库的 `End` 是全局的 —— 不可能同时正确。故新增两个
     内部辅助函数 `scs_big_endian()` / `scs_little_endian()`，在每个**系列专属**
     的命令包装里于 `SCS_Lock()` 之后调用：SCSCL 系列（`SCS_WritePos` /
     `SCS_RegWritePos` / `SCS_SyncWritePos` / `SCS_EnableTorque`）切大端，
     SMS_STS 与 HLS 系列（`SCS_WritePosEx` / `SCS_SyncWritePosEx` /
     `SCS_WriteSpeEx` / `SCS_WheelMode` / `SCS_SetMode` / `SCS_CalibrationOfs` /
     EPROM 解锁对 等）切小端。切换点放在互斥锁**之内**，与总线访问受同一把锁
     保护，不会与另一系列的帧交错。

  3. **新增公开接口 `SCS_SetEnd(uint8_t big_endian)`**（兼容升级，纯新增）。
     回读函数（`SCS_ReadPos(id)` / `SCS_ReadSpeed(id)` / …）在厂商库里是三套系列
     **共用**的实现，光凭 id 分不出该用哪套，只能由调用方先声明。写命令不需要
     调它 —— 系列专属包装会自己设好。

  4. **修正中位常量取值。** `Core/Src/app_freertos.c` 的 `STS_CENTER` 由 4095
     改为 **2048**，`SCS_CENTER` 由 60（调试期间被临时改成 0/2）改为 **500**。
     注释本就写着「中位」，但原值与注释矛盾。这两个值必须落在量程中段：位置
     寄存器是单圈绝对值，**0 与量程上限在物理上是相邻的同一个点**，目标停在那里
     时手推几度就会让读数从一端跳到另一端，位置环把误差算成「差一整圈」，于是
     顺着推力方向转满一圈才回来 —— 即上一个现象。即便字节序修好，取 0/2/4095
     这类值该现象**依然会出现**，故在 `PD` 区补了 `@warning` 说明。

  5. **文档口径修正。** `servo_scs.h` 里 `SCS_WritePos()` 的量程原写「0~1000
     对应 0~300°」，按 SCS0009 产品页更正为 **0~1024（10 位编码器）对应 0~300°、
     0.293°/步**，中位 500。同时补上字节序的背景说明与 `SCS_SetEnd()` 的用法。

  6. **未改动 `scslib/`**：厂商 11 个文件仍与上游逐字节可比（工程约定见
     V1.10.0）。厂商库自身在回读路径上的不一致（`ReadPos()` 的缓冲区分支在
     `scslib/SCSCL.c:111-113` 写死了大端，而其总线分支走 `SCS2Host()` 会跟随
     `End`；`ReadCurrent()` 的缓冲区分支 `scslib/SCSCL.c:192-194` 又按小端取）
     **仍然存在**，本次只在注释里标注，不做「修正」—— 两者至多只有一个是对的，
     改哪个都会破坏与上游的逐字节可比性。

- **影响范围**：
  - **行为改变**：`SCS_WritePos()`（SCSCL 系列写位置）的线上字节序由小端变为大端，
    SCS0009 从此收到正确的目标位置。`SCS_WritePosEx()` 等 SMS_STS/HLS 系列的行为
    **不变**（仍是小端，与原 `setEnd(0)` 一致）。
  - **接口**：`SCS_SetEnd()` 为新增，未改动任何已有函数签名、结构体或构建产物，
    **兼容升级**。
  - 未使用舵机总线的模块零影响。`gripper_task` 是唯一调用方。
- **验证状态**：已验证（编译层面）。`cmake --build --preset Debug --clean-first`
  全量重编，**0 error、0 新增 warning** —— 告警集合与改动前完全一致，仍只有既有
  三项（`oled_data.c` 4 处、`ColorIdentif.c` 2 处、`ops9_g491_uart3.c` 1 处）。
  现状 FLASH 48912 B / 9.33%，RAM 15896 B / 16.17%。
  **尚未上车验证**：字节序是否被舵机正确接受、转角是否符合预期，均需实机确认。
- **备注**：
  - **上车验证方法**：`servo_set_pos(id, 500)` 发中位。若舵机转到行程中段（约 150°）
    则字节序已正确；若它直接顶到行程尽头，说明仍然是错的（500 = 0x01F4，错序后
    变成 0xF401 = 62465，必然超量程被钳到上限）。
  - **已知残留风险**：`SCS_Lock()` 取锁失败时会降级为无锁执行（见 `servo_scs.h`
    的说明），那种情况下按系列切 `End` 理论上可能被另一任务打断。当前只有
    `gripper` 一个任务访问总线，暂不构成问题；若日后新增舵机任务需重新评估。
  - 回读路径（`SCS_FeedBack()` + `ReadXxx(-1)`，厂商文档推荐的「一次往返取全」
    用法）不受本次改动影响：缓冲区路径完全不经过 `End`，而厂商在那里写死的是
    大端 —— 即对 SCS0009 正确、对 STS3032 取位置会错。
  - 来源：飞特官方《通信协议高低字节问题》、飞特入门教程 FAQ 第 7 条、
    SCS15 & SCS115 手册内存表、SCS0009 产品页。
