#### V1.29.0 - 2026-10-10
- **修改类型**：新增
- **涉及模块**：应用层 / `app/ws2812.c` + `app/ws2812.h`
- **修改内容**：新增 WS2812 灯珠驱动（PB4 → TIM16_CH1, AF1；DMA 半字流方案，参考
  `E:\DownLoad\模块资料\WS2812` 的 F103 版驱动移植）。
  TIM16 配 PSC=0、ARR=211 → 周期 1.247us ≈ 802kHz（170MHz APB2）；每周期 DMA 往 CCR1 搬
  一个半字，高电平宽度编码 0/1 位（逻辑 1 = 119 tick ≈ 0.70us，逻辑 0 = 60 tick ≈ 0.35us，
  同时满足 WS2812 与 WS2812B 手册）；帧前/帧后各 100 个全低周期（≈125us ≥ 50us）做复位与
  锁存，后置段兼作帧尾低电平保持。API 只留 `WS2812_AllWhite()` / `WS2812_AllOff()` 两个
  函数；DMA Normal 模式发完即回 READY，可重复调用（帧发送中约 550us@10 灯，期间再调会被
  HAL_BUSY 丢弃）。
  ⚠ **依赖 CubeMX 重生成**：PB4 须从 `TIM3_CH1` 改到 `TIM16_CH1`，并新增 TIM16_CH1 的
  DMA（半字对齐、Normal 模式、开 DMA 通道中断）——未做之前 `htim16` / `hdma_tim16_ch1`
  不存在，全工程编译不过。
- **影响范围**：无（新增模块、零调用者）。PB4 原有 TIM3_CH1 的唯一用户是
  `BlockBasic_DualArmSetPos()` 的前级舵机写 CCR，已被 `BLOCK_USE_DUAL_ARM=0` 编除，
  改脚无功能损失；PB0 丝杆限位不动。
- **验证状态**：待测试 —— 实机未验证；位时序按 APB2 分频 1（170MHz）计算，落在手册
  容差内（T0H 353ns / T1H 700ns / 周期 1.25us）
- **备注**：灯带若 5V 供电，3.3V 数据线高电平处于 VIH 临界（0.7×VDD = 3.5V），点不亮时
  把灯带 VDD 降到约 4.3V 或加电平转换；灯珠数量改 `ws2812.h` 的 `WS2812_LED_NUM`
  （现默认 10，与参考工程一致）；驱动放 `app/` 是按用户要求，规范上更宜归
  `hardware/display/`。

#### V1.29.1 - 2026-10-10
- **修改类型**：修复
- **涉及模块**：应用层 / `app/ws2812.h`；CubeMX 生成文件 `Core/Src/tim.c`、`bydcar_g491vet6.ioc`
- **修改内容**：两处 ——
  ① **TIM16_CH1 的 DMA Peripheral Increment 误配为 ENABLE**（CubeMX 里把外设地址递增勾上了）。
  本方案 DMA 的目的地址是固定寄存器 CCR1，开了递增后每搬一个半字地址就往后走 2 字节，
  位流值被写进 TIM16 的其它寄存器（第 3 次传输就把 BDTR 写成 0 → 关掉主输出 MOE），
  数据线根本没送出完整位流，灯带收到乱数据 —— 实测现象：8 灯只亮 4 个，颜色随机
  （白/粉/红/绿）。改为 `DMA_PINC_DISABLE`；`tim.c` 与 `.ioc` 同步改，之后 CubeMX
  重新生成不会丢。⚠ 若 CubeMX 此刻正开着且有未保存的改动，先别保存（会覆盖回 ENABLE）。
  ② `WS2812_LED_NUM` 由 10 改为 **8**（实际焊接灯数，用户确认）。
- **影响范围**：WS2812 灯带显示
- **验证状态**：待测试 —— 编译通过；实机待烧录确认 8 灯全白/全灭
- **备注**：DMA1_Channel6 中断已由 CubeMX 自动启用（优先级 5），无其它配置缺失；
  若全白仍异常，检查灯带供电：8 灯全白 ≈ 480mA，欠压会掉灯/变色，必要时把亮度从
  255 降到 ~80 再试

#### V1.29.2 - 2026-10-10
- **修改类型**：修复
- **涉及模块**：CubeMX 生成文件 `Core/Src/tim.c`、`bydcar_g491vet6.ioc`
- **修改内容**：**V1.29.1 的修复被还原了** —— 工作区里 `PeriphInc` 又回到
  `DMA_PINC_ENABLE`（`tim.c:171`，`.ioc:36` 两处同步）。本次重新改回
  `DMA_PINC_DISABLE`。
  机理（与 V1.29.1 同）：DMA 目的地址是固定的 `TIM16_CCR1`(0x34)，开递增后每个半字
  地址 +2 → 0x34(CCR1)、0x36/0x38/0x3A/0x3C/0x3E/0x40/0x42 保留区、**第 9 个半字
  落到 0x44 = BDTR**，而缓冲前 100 个半字全是复位段 0 → `BDTR = 0` → **MOE 主输出
  关闭**，第 9 个周期（≈10us）后 PB4 彻底不再输出。加上喂进 CCR1 的只有偶数字节，
  位流本身就是错的。现象：**一个都不亮**，偶尔第一个灯珠被截断的乱码点亮一下。
- **影响范围**：WS2812 灯带显示
- **验证状态**：待测试（改回后需重新烧录）
- **备注**：⚠ **根因是 CubeMX 重新生成覆盖了手改**。只改 `tim.c` 会在下次 Code
  Generation 时再丢一次；须在 CubeMX 的 `TIM16 → DMA Settings → TIM16_CH1` 里把
  **Increment Address（外设侧）取消勾选**再 Generate。另：`WS2812_AllWhite/AllOff`
  的 `HAL_TIM_PWM_Start_DMA` 返回值未判，帧发到一半再调会被 `HAL_BUSY` 静默丢弃
  （当前两个调用点间隔远大于 550us，无实际影响）

#### V1.29.3 - 2026-10-10
- **修改类型**：新增（**临时诊断，测完必须还原**）
- **涉及模块**：应用层 / `app/ws2812.c` + `app/ws2812.h` + `Core/Src/app_freertos.c`
- **修改内容**：V1.29.2 修复后实测变为「**只有第一颗亮, 且是绿色**」(上电即如此, 之后
  不变)。分析：`WS2812_AllWhite()` 送的是全 1 位流, 192 个位元波形完全一致; 灯珠内部
  24bit 移位暂存器里**第一个位元落在 G 的最高位**, 所以「显示绿色」只可能意味着
  **只收到了 G 那 8 个位元、R/B 那 16 个位元根本没时钟进去** —— 这是**时间轴上**被截断,
  任何类比问题(电平临界/供电)都不可能刚好区分第 8 和第 9 个位元。
  而 `NLF_TASK` 上电只发一帧就阻塞在 `osThreadFlagsWait`(NF_AUTOSTART=0), WS2812 无
  自刷新 → 错误状态永久残留, 无法区分「帧被截断」还是「上电瞬间锁存到杂讯」。
  故加诊断：
  ① 新增 `WS2812_DebugRGB()` —— LED0 红 / LED1 绿 / LED2 蓝 / 其余全灭；
  ② 挂进 `FC_TASK` 的 10ms 循环（兼作周期刷新, 排除上电时序竞争）；
  ③ 临时注释掉 `NLF_TASK` 里那一次 `WS2812_AllWhite()`, 免得和诊断样式抢。
- **影响范围**：仅灯带显示；流程本身未改（`NLF_TASK` 只是少了上电那一次点灯）
- **验证状态**：待测试（等实机结果定性）
- **备注**：结果判读 —— **三颗按红/绿/蓝亮** = 数据通路正常, 原绿色是上电锁存杂讯,
  改成周期刷新即可；**只有 LED0 红** = 24bit 到了但下游断；**LED0 黑** = 只送到 8 个
  "0" 位元；**LED0 依旧绿** = 根本没收到本驱动的数据(杂讯/引脚接错)。
  另：**回滚清单** —— 删 `WS2812_DebugRGB()` 定义与声明、删 `FC_TASK` 里那行调用、
  恢复 `NLF_TASK` 的 `WS2812_AllWhite();`。
  待办候选：`WS2812_RST_PERIOD_NUM=100`(≈125us) 对 **WS2812B-V5 要求 >280us** 偏短；
  以及 V1.29.2 备注里那条「缓冲避在发送前就被覆写」的隐患仍未修

#### V1.29.6 - 2026-10-10
- **修改类型**：修复（**根因，实打实的规格违反**）
- **涉及模块**：应用层 / `app/ws2812.h`（`WS2812_RST_PERIOD_NUM`）；`app/ws2812.c`（撤掉 V1.29.5 的守衛）
- **修改内容**：用户给出 WS2812B 手册要点 —— **复位(RES) 要求 ≥280us 持续低电平**，
  对应手册坑点「复位时间不足 280us：**灯不刷新**、偶发错位」。
  而本驱动 `WS2812_RST_PERIOD_NUM = 100` → 100 × 1.247us = **125us**，不足一半
  （原值是按老手册的 50us 取的）。**灯珠收到完整一帧也不锁存 → 永远显示上电时
  随机锁存的那个颜色（实测绿），怎么重发都不刷新** —— 这正是从头到尾「静止不动」
  的根因。改为 **300**（300 × 1.247us ≈ **374us**，留余量）。
  顺带撤掉 V1.29.5 的 `ws2812_busy()` 守衛：加它之后实测从「乱闪」变成「一个都不亮」，
  `HAL_DMA_Init` 结尾确实置 `State = READY`（已读源码确认），故卡住只能是 **DMA 一次都没
  跑完**（`State` 停在 BUSY）→ 守衛把每次发送都挡死。为「单变量验证复位时长」先移除，
  把该防護的**正确写法（判据用 DMA `CCR.EN` 位，而非 HAL `hdma->State`）**以注释形式
  留在 `ws2812.c` 里，接回流程点灯前必须补上。
- **影响范围**：一帧从 392 个周期（490us）变为 792 个周期（≈990us），仍远小于 10ms 刷新间隔；
  缓冲 784 → 1584 字节
- **验证状态**：待测试（已 `--clean-first` 全量重编通过，`ws2812.c` 无告警）
- **备注**：教程其余要点对照 —— **GRB 顺序 ✓**（`data[3]={g,r,b}`）、**逻辑 0/1 时序 ✓**
  （353ns/700ns，周期 1.247us）、**PWM+DMA 半字/正常模式 ✓**、**OCxPE 预装载 ✓**
  （HAL 强制开）。仍待人工确认的硬件项：**共地**（不共地极易乱闪/误码，头号嫌疑）、
  **5V 供电**（3.3V 亮度低）、DI 串 330Ω（≤8 颗可不加）、长灯带多点补电。
  另教程「不要在高频控制循环里频繁刷新灯光」—— `FC_TASK` 现在 10ms 刷一次属诊断用，
  验证完会改成只在状态变化时刷

#### V1.29.7 - 2026-10-10
- **修改类型**：修改（**位元时序对齐手册标准值**）
- **涉及模块**：应用层 / `app/ws2812.h`
- **修改内容**：V1.29.6 后实测变为「**前五个是白灯、第六个是红的**」。分析：
  流水灯每 0.5s 走一格，却有 5 颗**同时**亮着 ⇒ 是**拖尾** —— 前面几轮的
  「灭」没有把它们清掉。而「灭」靠的是那些全 0 灯送出的位元。机制：
  **一连串"0"位元的短高电平在临界电平下被灯珠当作"没有高电平"，看起来就是
  一条连续低电平 → 被当成复位 → 整帧从中途被截断 → 后面的灯收不到数据、
  保持上一轮颜色**（拖尾）。
  用户提供的手册标准值：逻辑0 = 高 0.4us + 低 0.85us；逻辑1 = 高 0.8us + 低 0.45us
  （周期 1.25us）。本驱动原取 119 / 60 tick（0.70us / 0.353us），**比手册短约 12%**。
  换算到 `ARR=211`（212 tick 周期）正好是 **136 / 68 tick**，低位自动对上
  （447ns / 847ns）—— 说明 ARR 本来就对，只是两个占空比偏窄。已改。
- **影响范围**：WS2812 位时序；`ARR`/`PSC`/复位时长均未动
- **验证状态**：待测试（编译通过）
- **备注**：⚠ 这是**做余量**，不是根治 —— 根子还是 **3.3V 驱动 5V 灯带
  （VIH = 0.7×5 = 3.5V，差 0.2V）**。真正的解法：灯带 VDD 串一颗 1N4148 降到
  ~4.3V（VIH → 3.0V），或加 74HCT245/74AHCT1G125 电平转换。另外**共地**务必确认
  （教程坑点第 2 条：不共地极易乱闪、误码）

#### V1.31.0 - 2026-10-10
- **修改类型**：修改（**驱动换成 keysking 教程的库，并做 7 处适配**；接口不兼容 → 已加别名）
- **涉及模块**：应用层 / `app/ws2812.c` + `app/ws2812.h`；生成区 `Core/Src/tim.c`、
  `bydcar_g491vet6.ioc`、`Core/Src/main.c`
- **修改内容**：
  **① 根因最终判定（本日一整天的结论）**：灯珠 `VIH = 0.7 x VDD`，5V 供电时 = **3.5V**，
  而 MCU 推挽只给 3.3V。三个现象同源，互相印证：
    · 送**全白**没反应（3.3V 的短脉冲跨不过门限，灯珠看不见）；
    · 送**全灭**也不熄（同理，0 位元也看不见，移位暫存器保持原值）；
    · 只有**舵机大动作**才亮杂色（馬達大电流的尖峰在共用地上把参考点抬起，瞬间
      跨过 3.5V，灯珠才「看到」东西 —— 但那是噪声不是数据）。
  **⇒ "要靠舵机噪声才亮" 本身就是"我们的信号一直在门限之下"的铁证。**
  **② 采用 keysking 的方案（他文档里写得很明确）**：`Debug = Serial Wire` 释放 PB4、
  PB4 = **Alternate Function Open Drain**、**外接 5V 上拉电阻（1k~4.7k）**。
  开漏时 MCU 只拉低，高电平由电阻抬到 **5V**，幅度就够了。PB4 是 **FT_c（5V 耐受）**，安全。
  **③ keysking 代码在本工程上的 7 处问题（已修）**：
    a. `HAL_TIM_PWM_Start_DMA(&htim3,...)` —— 他的板子 PB4 = TIM3_CH1，本工程是
       **TIM16_CH1**；且 `htim3` 上没 link DMA → `HAL_DMA_Start_IT(NULL,...)` →
       **HardFault**。改成 `&htim16`。
    b. **缺后置复位** —— 原版只有前置 `RST_PERIOD_NUM` 个 0，DMA 发完后 CCR 停在
       最后一个位元的值，数据线继续抖 → 灯珠等不到复位 → **不锁存**。缓冲改成
       `[前置][数据][后置]`。
    c. 占空比 `66 / 21` 是给 **72MHz / ARR=89** 的（他文档第一句就是 HCLK=72）；
       本工程 170MHz，按 170/72≈2.36 放大 → **156 / 50**（时长与原版一致）。
    d. 位元序原码发 **R→G→B**，WS2812 标准是 **GRB** → 加 `WS2812_BYTE_ORDER_RGB`
       宏（默认 0 = GRB）。
    e. `HAL_Delay` → `osDelay`（FreeRTOS 里 HAL_Delay 是忙等，不让出 CPU）。
    f. 补边界保护：`led_id` 越界、`steps==0` 除零。
    g. 补「发送中」防护（判据 = DMA 通道的 `CCR.EN` 位）。
    另加 `WS2812_AllWhite()` / `WS2812_AllOff()` 两个**别名**，流程里的呼叫点不用改。
  **④ 试过 PD7 又回退**：PD7 = TIM2_CH3 的复用号是 **AF2 不是 AF1**（第一次写 AF1，
  PD7 毫无输出）；TIM2 那段是手写进生成区的，CubeMX 重新生成后被覆盖，已回退到
  PB4/TIM16_CH1。**CubeMX 侧最终状态**：`PB4.GPIO_ModeDefaultPP=GPIO_MODE_AF_OD`、
  `Period=212`（213 tick = 798kHz）、DMA TIM16_CH1 且 `PeriphInc=DISABLE`。
- **影响范围**：WS2812 显示；**接口不兼容**（`WS2812_AllWhite/AllOff` 变成别名，
  keysking 的 `ws2812_set/update/...` 成为主接口）
- **验证状态**：待测试（`--clean-first` 全量重编通过，`ws2812.c` 零告警）
- **备注**：⚠ **还差一颗电阻**：**PB4 必须外接 1k~4.7k 到 +5V**。没有它，开漏的
  「高电平」是浮空，灯带一个位元都收不到（全黑）。这是整个方案的命门。
  另：舵机能干扰得这么明显，说明**走线/接地**仍需整理（数据线别和舵机线并排走、
