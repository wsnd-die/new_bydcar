#### V1.17.0 - 2026-09-28
- **修改类型**：新增（**兼容升级** —— `NLF_RunFlow()` 的签名与调用方式未变，
  只是从空壳变为完整实现；`task_send()` / 事件队列通路保持原样）
- **涉及模块**：

  - 应用层 / `app/worker_task.h`（仅 `NLF_RunFlow()` 的文档注释）
- **修改内容**：

  按用户 2026-09-28 的要求，把比赛流程编排进 `NLF_RunFlow()`，
  并以「不再扫描二维码」为前提取舍数据来源。

  1. **流程顺序表**（`worker_task.c` 4.2 节）。旧版 `NLF_TASK` 用的是
     `Navafter_mode[]` / `NavafterNum[]` 两张平行数组，本实现合成一个结构体：

     ```c
     typedef struct { SystemMode_t mode; uint8_t times; } NF_Stage_t;
     static const NF_Stage_t NF_STAGES[] = {
         { Event_LinFolL,    1u },   /* 左循迹: 收集物块 */
         { Event_FindCircle, 5u },   /* 找圆 ×5: 一个个放物块 */
         { Event_LinFolR,    1u },   /* 右循迹: 收集奖杯 */
         { Event_PlaceDown,  3u },   /* 放奖杯 ×3 */
     };
     ```

     与旧表的差异：**两个 `Event_QRCode` 项已删除**（按用户决定不再扫二维码）。
     其余各项的 `times` 与旧代码逐项一致。

  2. **沿用旧代码的「中继站」结构**。旧 `NLF_TASK` 里每个阶段跑完都
     `task_send(Event_Navigation)`，由 `Event_Navigation` 分支去查顺序表决定下一项。
     本实现保留这个结构：新增 `NF_Stage_Navigation()` 调用 `NF_DispatchNext()`
     派发下一阶段，置 `NLF_Request(next)`；`NF_DispatchNext()` 的推进规则
     （先派发当前项、再自减、减到 0 才进下标）与旧代码逐行一致。

     前进方式由旧的 `task_send()` 改为 `NLF_Request()`（线程标志）。
     原因见 `worker_task.h` 的契约：`NLF_Request` 直接置标志，少一趟
     「NLF_TASK → 事件队列 → defaultTask → 再置标志」的调度器往返。
     **事件队列通路原样保留**，留给将来的上位机/调试指令。

  3. **硬编码默认值集中在 `worker_task.c` 顶部（4.1 节），带醒目注释**，
     按用户要求。共四处，每处都标了「★ NX 接入点」：

     | 常量 | 作用 | 旧来源 |
     |---|---|---|
     | `NF_RANK[3]` | 奖杯放置顺序（亚军→冠军→季军） | 旧 `rank[3]` |
     | `NF_TROPHY_SLOT[4]` | 奖杯 → 转盘工位 | 旧 `Slop_dirjang()` |
     | `NF_PLACE_HEIGHT[4]` | 放置丝杆高度 37/28/17 mm | 旧 `PlaceDown` 三分支 |
     | `NF_SLOT_COLORS[5]` | 五个槽位的物块颜色 | 旧颜色传感器收集 |

     NX 接入时**只需改 `NF_FlowSeed()` 的函数体**（加 `NLF_RunFlow` 入口处调用），
     流程主体一行不用动。

  4. **`NF_TROPHY_SLOT[]` 的取值依据**：旧的 `Slop_dirjang()` 读全局 `Jang_Num`
     （QR 右码 1~6）查 `T2[Jang_Num-1][i]`，返回 `3-i`。本表取
     `T2` 第 1 行 `{金, 银, 铜}` 的倒序映射，即 `Jang_Num=1` 时 `Slop_dirjang()`
     的输出（冠军→3、亚军→2、季军→1），逐项等价。
     **未采用「直接写 `Jang_Num`」的做法** —— 那等于在应用层伪造一次 QR 扫描结果，
     正是本次要移除的东西；`Slop_dirjang()` 函数本身**保留未动**，
     将来 NX 若回传 QR 图案号可直接换回。

  5. **`Circle_Follow()` 改为显式 while 循环调用**。这是与旧代码的**必要差异**：
     `algorithm/Circle_base.c` 里它是**单拍函数** —— 不阻塞、不自循环、
     没有退出条件，跑一次只发 10ms 的一拍电机指令，退出判定是它自己写的
     `g_circle_dir`。旧代码把它放在按拍的轮询状态机里所以能跑；搬到阻塞式的
     `NLF_RunFlow()` 后必须由调用方循环。同理由 `TT_RotateByQR()`
     （每次只转一格 + 内部 `osDelay(500)`）也改为循环到返回 false。

  6. **找圆阶段增加 30s 超时**（`NF_CIRCLE_TIMEOUT_MS`）。旧代码没有超时，
     而 `NX_GetCircleDir()` 只在收到新帧时更新、无帧时沿用 `s_last_dir`（初值 `'?'`），
     所以上位机没接或没识别到圆心时 `g_circle_dir` **永远不会**变成 `'O'` ——
     没有这道兜底，流程会永久卡死在找圆里。超时后打日志、刹停、回中继站继续下一项。

  7. **循迹两段打桩**（`NF_Stage_LinFolL` / `NF_Stage_LinFolR`）。按用户决定，
     循迹控制器（`algorithm/Trace_base.c`，已随 V1.6.0 删除）本次不恢复，
     先打日志直接跳过，把骨架串通。真实现补进来时要做的三步已写在函数注释里。

  8. **`NF_AUTOSTART` 宏（默认 1）**：复刻旧 `NLF_TASK` 起来就
     `task_send(Event_Navigation)` 自动开跑的行为，同时保留置 0 即可关掉的开关。
     起跑点放在 `NLF_Fuction()` 里用一个 `static bool s_kicked` 门闩锁住 ——
     `NLF_Fuction()` 是被 `NLF_TASK` 的 `for(;;)` 反复调的，没有这个门闩，
     每轮都会把流程拽回 `Event_Navigation`，而 `NF_Stage_Navigation()` 每次都推进
     顺序表计数器，几轮就把整张表烧穿、直接跳到 `Event_GoHome`。

- **修改类型**：修复（**兼容升级** —— 任务名与栈深是内部实现；

  - 构建配置 / `bydcar_g491vet6.ioc`

- **修改内容**：

  修复三处使「流程根本跑不起来」的断点。这三处是**互相独立的历史缺陷**，
  此前因为应用层整体被 `--gc-sections` 回收而没有暴露。

  1. **`nlfTaskHandle` / `fcTaskHandle` 从未被赋值（恒 NULL）**。

     `worker_task.c` 里它们是 `= NULL` 定义，全工程**没有任何写入点**；
     而 `MX_FREERTOS_Init()` 把 `osThreadNew()` 的返回值赋给了
     `nav_taskHandle` / `findcircle_TASKHandle`。于是：

     ```c
     void NLF_Request(SystemMode_t mode) {
         s_nlf_pending = mode;
         if (nlfTaskHandle != NULL) {          /* ← 恒假 */
             osThreadFlagsSet(nlfTaskHandle, NLF_FLAG_RUN);   /* ← 一次都没执行过 */
         }
     }
     ```

     → `NLF_TASK` 永久阻塞在 `osThreadFlagsWait`，`NLF_RunFlow()` 一次也没执行过。

     修法：在 `MX_FREERTOS_Init()` 的 `USER CODE BEGIN RTOS_THREADS` 区
     （重新生成不会覆盖）转存句柄：

     ```c
     nlfTaskHandle = NLF_TASKHandle;
     fcTaskHandle  = FC_TASKHandle;
     ```

  2. **`NLF_TASK` 实际只有 1KB 栈，与声明不符**。

     `app/worker_task.h` 声明 `NLF_TASK_STACK_WORDS = 1024`（4KB）并说明理由，
     但 `app_freertos.c` 里 `osThreadNew(NLF_TASK, ...)` 用的是
     `nav_task_attributes`（`256 * 4` = 1KB）；同文件 USER CODE 区那两组
     `fcTask_attributes` / `nlfTask_attributes`（4KB）**定义了却从没传给
     `osThreadNew`**，是纯死代码。

     风险是实的：`servo_scs.h` 要求 SCS 调用方留 ≥1KB 栈余量，而 V1.17.0 的流程
     要在 NLF_TASK 里跑 `TT_RotateByQR()` → `BlockBasic_TurntableTo()` → SCS 总线，
     沿途还有多处 `printf`。

     修法：改 `.ioc` 的 `FREERTOS.Tasks01`，`nav_task` 栈深 `256 → 1024`；
     同步改 `app_freertos.c` 生成区；删除 USER CODE 区那两组死代码属性。
     **改 `.ioc` 而非只改生成代码**，否则重新生成会被冲回 1KB。

  3. **任务名误导**：`.ioc` 里两个任务叫 `findcircle_TASK` / `nav_task`，
     而入口函数是 `FC_TASK` / `NLF_TASK` —— 名字与职责完全对不上，
     排查时极易看错。已在 `.ioc` 里改名为 `FC_TASK` / `NLF_TASK`（与入口函数同名），
     生成区同步。

- **影响范围**：

  - 任务优先级**未改动**（`FC_TASK` 仍 `osPriorityLow`=8、`NLF_TASK` 仍
    `osPriorityHigh`=40），避免改变调度行为。
  - `NLF_TASK` 的 RAM 占用 +3KB（`configTOTAL_HEAP_SIZE` 为 16384，
    见 `.ioc`），当前 `bss` 增量实测仅 +160 B（栈是运行时从 FreeRTOS 堆切的，
    不计入 `bss`）。
  - `nm` 确认 `findcircle_TASK` / `nav_task` 符号已消失，
    `FC_TASKHandle` / `NLF_TASKHandle` 已定义。

- **验证状态**：**部分验证** —— 编译通过、符号表正确。**句柄是否真的被写进去
  需要上机或调试器确认**（断点打在 `worker_task.c` 的 `NLF_Request()`，
  看 `nlfTaskHandle != NULL` 是否成立）。

- **备注**：

  1. **【已知未修】`FC_TASK` 的职责与其文档不符**。`worker_task.h` 把 `FC_TASK`
     描述为「10ms 角度环」，但 `app_freertos.c` 里它实际只调
     `FC_Fuction()`（每 100ms 重发一次 NX 找圆模式），**真正的角度环跑在
     另一个任务 `angle_Task` → `AC_Fuction()` → `Angle_Fuction()` 里**，
     优先级 `osPriorityLow`(8)。
     这意味着文档里「FC_TASK 必须能抢占 NLF_TASK，否则控制周期被拉长」那条
     约束**当前不成立**（角度环任务优先级 8 低于 NLF_TASK 的 40）。
     本次**未动它** —— 重新划分任务职责会改变实时行为，属于独立改动，
     应单独评估并记录。
  2. **【已知未修】`FC_Fuction()` 的 100ms NX 模式重发**在 V1.17.0 之后是冗余的
     （`NX_ApplyMode()` 只在模式变化时发帧），但无害，一并留待上面那次职责梳理。
     附带说明：`FC_Fuction()` 内部有 `osDelay(100)`，所以 `FC_TASK` 的实际节拍是
     ~110ms 而非外层 `osDelay(10)` 看上去的 10ms —— 这一点在任何「把周期任务挂到
     FC_TASK 上」的改动里都要注意。
  3. `angle_TaskHandle` / `angle_Task_attributes` 未动。

#### V1.18.0 - 2026-09-28
- **修改类型**：新增（**兼容升级** —— 纯新增文件，不改动任何既有模块的接口）
- **涉及模块**：硬件驱动层 / `hardware/sensors/key.c`、`hardware/sensors/key.h`（新增）
- **修改内容**：

  按用户要求（2026-09-28）新增按键消抖驱动，适配两个开关：

  | 按键 | 引脚 | 用途 |
  |---|---|---|
  | `KEY_LIMIT` | PB0 | 限位开关 |
  | `KEY_START` | PA0 | 启动开关（`main.h` 的 `START_Pin`） |

  1. **消抖算法：连续采样确认法**。每次 `Key_Update()` 采一次原始电平，
     连续 `KEY_DEBOUNCE_SAMPLES` 次都读到与当前稳定态相反的电平才认账翻转；
     抖动期间只要有一拍回到原电平，计数立即清零。
     与 `algorithm/Circle_base.c` 的 `CIRCLE_O_STABLE_CNT` 是同一套思路。

  | 动作 | OPS9 原始输出 |
  |---|---|
  | 往车头方向推 | `y` 增大 |
  | 往左推 | `x` 减小 |
  | 逆时针转 | `yaw` 增大 |

  而工程约定（CLAUDE.md 第 3 节）是 X=前方、Y=左方、yaw CCW 为正。
  据此换算（下标 `_o` = OPS9 原始，`_w` = 工程约定）：

  ```
  x_w   =  y_o
  y_w   = -x_o
  yaw_w = yaw_o          ← 不变号
  ```

  **`yaw` 为什么不反号**：由约束 `M·(0,1)=(1,0)`、`M·(-1,0)=(0,1)` 解出
  `M = [[0,1],[-1,0]]`，`det(M) = +1` —— 这是**纯旋转**（绕 −90°）而不是
  镜像。镜像才会让手性翻转、需要给 `yaw` 反号；这里不需要。
  这也与实测的「逆时针 = yaw 增大」和约定的「CCW 为正」方向一致互为印证。

  `pitch` / `roll` 只绕 Z 做坐标换算，不受影响，保持原样透传。

  2. **启动键触发放在 `KEY_TASK` 里**（`app_freertos.c`）：

     ```c
     Key_Update();
     if (Key_WasPressed(KEY_START)) {
         printf("[KEY] 启动键 -> NLF_Request(Event_Navigation)\r\n");
         NLF_Request(Event_Navigation);
     }
     osDelay(10);
     ```

     - 用 **`Key_WasPressed()`（边沿，读后清）** 而不是 `Key_IsPressed()`（电平）：
       后者只要按着就恒真，会每 10ms 触发一次，每圈把流程拽回中继站。
     - `KEY_TASK` 本来就是 10ms 一拍喂 `Key_Update()` 的地方，
       顺手做触发，不新增任务、不新增轮询点。

  3. **【排查结论】不能放在 `StartDefaultTask` —— 那里的循环体永远不会执行。**

     此前的版本把启动键判断写在 `StartDefaultTask` 的
     `task_recive()` **之后**，那段代码**一次也没跑过**。原因是：

     ```c
     // app/banyuntask.c:30-43
     TaskCommand_t task_recive(void) {
         if (xQueueReceive(systemEventQueue, &receivedCmd,
                           portMAX_DELAY) == pdPASS) { ... }   // ← 永久阻塞
     }
     ```

     `portMAX_DELAY` 表示无限等待，而 `task_send()`（队列唯一的生产者）
     **全工程零调用者** —— 所以 `StartDefaultTask` 的循环体在第一次
     `task_recive()` 之后就再也没返回过，写在其后的任何代码都不会执行。
     这大概率就是用户反馈"按键没反应"的真正原因。

     > 这同时意味着：`StartDefaultTask` 目前**实际上只是"开机初始化 +
     > 阻塞在空队列上"**。调度器（`task_recive → NLF_Request`）这条设计上
     > 的通路，因为没有生产者而处于休眠状态 —— 与 V1.17.0 备注里
     > "事件队列通路原样保留，留给将来的上位机/调试指令"一致，属已知状态。
