#### V1.14.1 - 2026-09-26
- **修改类型**：修改（不兼容升级 —— `ops9_g491_uart3` 与 `uart2_tbop10` 各有一个
  导出函数改名/新增；两处调用方已同步，全工程无遗留引用）
- **涉及模块**：
  - 抽象设备层 / `device/ops9_g491_uart3.c`、`ops9_g491_uart3.h`
  - 硬件驱动层 / `hardware/bus/uart2_tbop10.c`、`uart2_tbop10.h`
  - Core / `Core/Src/usart.c`（USER CODE 区）
- **修改内容**：

  1. **USART3（OPS9）的接收从「逐字节中断」改为「DMA + IDLE」。**
     V1.14.1 之前 `start_rx_it()` 调 `HAL_UART_Receive_IT(s_huart, &s_rx_byte, 1u)`，
     每收 1 字节进一次中断喂状态机。现改为 `HAL_UARTEx_ReceiveToIdle_DMA()`
     一次挂 64 字节缓冲，总线 IDLE 或缓冲收满时回调，回调里 `ops9_input()`
     批量喂状态机。

     **为什么必须用 IDLE 版而不是定长 `HAL_UART_Receive_DMA`：**
     `HAL_UART_Receive_DMA` 只在**收满整整 Size 字节**时才触发完成回调
     （见 `stm32g4xx_hal_uart.c` 的 `UART_DMAReceiveCplt`）。而 OPS9 一帧是
     `0x0D 0x0A` + 24B payload + `0x0A 0x0D` = **28 字节**
     （`OPS9_FRAME_SIZE`），缓冲是 64 字节 —— 定长接收要凑满 64 字节才解析
     一次（≈2.3 帧），尾部残留会一直压在缓冲里；帧流一停就彻底不再更新。
     `HAL_UARTEx_ReceiveToIdle_DMA` 会清 `IDLEF` 并使能 `IDLEIE`，IDLE 一到
     即回调，变长帧才对得上。

  2. **腾出 `HAL_UARTEx_RxEventCallback` —— 本次最关键的一处结构改动。**

     `HAL_UARTEx_RxEventCallback` 是 HAL 的 weak 回调，**全工程只能有一个定义**。
     此前这个定义在 `hardware/bus/uart2_tbop10.c`（只管 USART2）。USART3 改用
     DMA-IDLE 后同样需要它，于是：

     | 文件 | 改动 |
     |---|---|
     | `hardware/bus/uart2_tbop10.c` | 原 `HAL_UARTEx_RxEventCallback` **改名为** `UART2_RxEventCallback` |
     | `hardware/bus/uart2_tbop10.h` | 在既有 `#if LEGACY_USART2_ODOM_ENABLE` 块内加声明 |
     | `Core/Src/usart.c` | **新增唯一的** `HAL_UARTEx_RxEventCallback`，按 `Instance` 分发 |

     `usart.c` 不做任何实际处理，只转发：
     ```c
     void HAL_UARTEx_RxEventCallback(UART_HandleTypeDef *huart, uint16_t Size)
     {
       if (huart->Instance == USART2)      UART2_RxEventCallback(huart, Size);
       else if (huart->Instance == USART3) OPS9_G491_UART3_RxEventCallback(huart, Size);
     }
     ```
     这样依赖方向是 `Core → device / hardware`，与既有的
     `HAL_UART_RxCpltCallback` / `HAL_UART_ErrorCallback`（本来就在 `usart.c`
     的 `USER CODE BEGIN 1` 区）一致。若改成在 `uart2_tbop10.c` 里加 USART3
     分支，会让硬件层反向依赖设备层，故未采用。

  3. **`Core/Src/usart.c` 的 `HAL_UART_RxCpltCallback()` 定义被删除。**
     USART2 / USART3 都走 DMA-IDLE，不会再走 RxCplt 路径。保留一个空定义会
     **遮蔽 HAL 的 weak 实现**，使将来任何串口想用 `HAL_UART_Receive_IT()` 时
     收不到完成回调。删掉后该符号回落为 HAL weak（`.elf` 中为 `W`）。

  4. **关掉半传输（HT）中断。** `HAL_UARTEx_ReceiveToIdle_DMA` 内部经
     `HAL_DMA_Start_IT` 会把 `DMA_IT_TC | DMA_IT_HT | DMA_IT_TE | DMA_IT_DME`
     一并打开；而 `UART_DMARxHalfCplt` 在 `ReceptionType == TOIDLE` 时**同样
     调用** `HAL_UARTEx_RxEventCallback`。不处理的话，64 字节缓冲收到 32 字节
     就会触发一次回调，一次接收被切成两截。故在重挂后补
     `__HAL_DMA_DISABLE_IT(&hdma_usart3_rx, DMA_IT_HT);`。
     为此在 `ops9_g491_uart3.h` 新增 `extern DMA_HandleTypeDef hdma_usart3_rx;`
     （沿用 `uart2_tbop10.h` 对 `hdma_usart2_rx` 的既有声明方式；
     `Core/Inc/usart.h` 只导出了 `huart1~5`，没有导出 DMA 句柄）。

  5. **重挂前清错误标志。** `start_rx_dma()` 里加
     `__HAL_UART_CLEAR_FLAG(s_huart, UART_CLEAR_OREF | UART_CLEAR_FEF | UART_CLEAR_NEF);`
     与 `uart2_tbop10.c:151/162` 的先例一致 —— ORE 未清时重新挂接收会立刻再报错。

  6. **顺手清掉两处死符号**：`device/ops9_g491_uart3.c` 的
     `static UART_HandleTypeDef s_owned_huart3;`（全文件零引用）与
     `device/ops9_g491_uart3.h` 的 `void OPS9_G491_UART3_IRQHandler(void);`
     （只有声明、无定义、零调用）。

#### V1.14.2 - 2026-09-26
- **修改类型**：修复（兼容升级 —— 驱动对外接口未变）
- **涉及模块**：
  - 硬件驱动层 / `hardware/sensors/hwt_imu.c`、`hwt_imu.h`
  - Core / `Core/Src/i2c.c`（USER CODE 区）、`Core/Src/stm32g4xx_it.c`（USER CODE 区）
- **修改内容**：

  1. **背景：工作区里有一处半途改动。** 本版之前 I2C3 读的是阻塞式
     `HAL_I2C_Mem_Read()`（三处：`hwt_imu.c` 的 `HWT_IMU_ReadReg()`、
     `HWT_IMU_Poll()` 的块读与退化路径）。工作区未提交的改动把这三处换成了
     `HAL_I2C_Mem_Read_DMA()`，**但只改了调用点**，两件配套的事都没做。

  2. **问题一（致命）：I2C3_EV/ER 的 NVIC 从未使能。** 三处独立核查都确认：
     - `Core/Src/i2c.c` 的 `I2C3_MspInit()` 里**没有任何 NVIC 配置**
       （对比 `USART3_MspInit()` 末尾有 `HAL_NVIC_SetPriority/EnableIRQ`）；
     - `Core/Src/stm32g4xx_it.c` 的 IRQHandler 全集只有 DMA1_Channel1~4、
       USART1/2/3、UART4/5、FDCAN2_IT0 —— **没有 `I2C3_EV_IRQHandler` /
       `I2C3_ER_IRQHandler`**；
     - `bydcar_g491vet6.ioc` 的 NVIC 清单里也没有 —— **不是生成代码过期，
       是 CubeMX 从来没有勾过这两项**。

     这一条是致命的：`HAL_I2C_Mem_Read_DMA()` 启动 DMA 后**立刻**
     `return HAL_OK`（HAL 源码注释原文：*"The I2C interrupts must be enabled
     after unlocking current process..."*），它只开**外设侧** `CR1` 的中断位，
     而**地址相位**（发完内存地址后的 repeated START、ADDR/TC/NACK 处理）
     全在 ISR 里推进。NVIC 不接通 → ISR 永不执行 → 传输永远完不成，
     `hi2c3.State` 卡在 `HAL_I2C_STATE_BUSY_RX`。之后每次调用都返回
     `HAL_BUSY`，IMU 完全读不出数据。

  3. **问题二：非阻塞 API 之后直接读缓冲是竞态。** 即使把 NVIC 补上，
     `HAL_I2C_Mem_Read_DMA()` 返回时数据还在路上，原调用点却立刻解析
     `buf` / `s_raw`。必须补上「等完成」这一步。

  4. **补 NVIC**（`Core/Src/i2c.c` 的 `I2C3_MspInit`，`USER CODE BEGIN
     I2C3_MspInit 1` 区）：
     ```c
     HAL_NVIC_SetPriority(I2C3_EV_IRQn, 5, 0);
     HAL_NVIC_EnableIRQ(I2C3_EV_IRQn);
     HAL_NVIC_SetPriority(I2C3_ER_IRQn, 5, 0);
     HAL_NVIC_EnableIRQ(I2C3_ER_IRQn);
     ```
     优先级 5/0，与 DMA1 各通道、USART3 保持一致。

  5. **补两个中断入口**（`Core/Src/stm32g4xx_it.c` 的 `USER CODE BEGIN 1` 区）：
     `I2C3_EV_IRQHandler()` → `HAL_I2C_EV_IRQHandler(&hi2c3)`；
     `I2C3_ER_IRQHandler()` → `HAL_I2C_ER_IRQHandler(&hi2c3)`。
     同时在该文件的 `USER CODE BEGIN EV` 区补 `extern I2C_HandleTypeDef hi2c3;`
     （该文件取句柄一律走显式 `extern`，沿用既有风格）。

  6. **`hwt_imu.c` 补上完成同步。** 新增：

     | 符号 | 作用 |
     |---|---|
     | `s_i2c_done` | 二值信号量，初值 0 |
     | `s_i2c_xfer_err` | volatile，本次传输成功/出错 |
     | `HAL_I2C_MemRxCpltCallback()` | 完成 → 清 err + release |
     | `HAL_I2C_ErrorCallback()` | 出错 → 置 err + release |
     | `hwt_imu_i2c_read()` (static) | 三处调用点收敛到此 |

     `hwt_imu_i2c_read()` 的时序：惰性建信号量 → 排空残留令牌 →
     `HAL_I2C_Mem_Read_DMA()` → `osSemaphoreAcquire(HWT_IMU_TIMEOUT_MS)` →
     返回。**对外语义与 V1.14.2 之前的 `HAL_I2C_Mem_Read()` 一致**
     （同样阻塞到数据到手、同样受 `HWT_IMU_TIMEOUT_MS` 约束），区别只在搬字节
     的活儿交给了 DMA。

     出错回调也 release，是为了让发起方立刻返回而不是空等满超时。
     超时分支调 `HAL_I2C_Master_Abort_IT()`，把 `State` 从 `BUSY_RX` 拉回，
     否则后续调用会一直 `HAL_BUSY`。

  7. **`osSemaphoreRelease` 的 ISR 安全性经查证。** 本工程的 CMSIS-RTOS2
     封装（`cmsis_os2.c`）里它显式判 `IS_IRQ()`，中断上下文走
     `xSemaphoreGiveFromISR` + `portYIELD_FROM_ISR`，非中断上下文才走
     `xSemaphoreGive`。故可直接在 HAL 回调里调用。（对照：裸的
     `xSemaphoreGive` 是**不能**在 ISR 里用的。）

  8. **调度器未启动时的退化路径。** `hwt_imu_i2c_read()` 在
     `osKernelGetState() != osKernelRunning` 时不 acquire 信号量，改为轮询
     `hi2c3.State` —— 因为 `osSemaphoreAcquire()` 会走进调度路径，
     调度器未启动时是危险的。与 V1.10.0 在 `ftBus_Delay()` / `SCS_Lock()`
     上踩过的坑同一处理口径。实际上本驱动目前只在 `FC_TASK` 内被调用
     （`device/HWT906.c:53/84` ← `app/worker_task.c:81/92`），正常走不到这条。

  9. **`hwt_imu.h` 的文档改写。** 原 `@note` 写着：「读数据用阻塞式
     `HAL_I2C_Mem_Read`。Core/Src/i2c.c:137 其实已经配好并链接了 I2C3 的 RX
     DMA 通道, 但本驱动没有用它 —— **26 字节量级 DMA 收益不明显, 却要额外引入
     传输完成同步**。」这半句判断是对的，26B @400kHz 只有约 0.65 ms；改用 DMA
     换来的不是速度，而是让地址相位/收尾由中断承担。注释已按新实现改写，
     并补上「只在任务上下文调用」的 `@warning`。
