#### V1.11.0 - 2026-09-25
- **修改类型**：新增（兼容升级）
- **涉及模块**：
  - 硬件驱动层 / `hardware/sensors/hwt_imu.c`、`hwt_imu.h`
  - 抽象设备层 / `device/pose_data.h`、`device/HWT906.c`、`device/HWT906.h`
  - 应用层 / `Core/Src/app_freertos.c`（**仅临时调试脚手架**，见备注 1）
- **修改内容**：

  1. **根因：HWT906 是九轴模块，驱动只读了姿态角一路。**
     V1.11.0 之前 `HWT_IMU_Poll()` 全函数只有一次传输：
     `HAL_I2C_Mem_Read(&hi2c3, 0x50<<1, 0x3D, 6 字节)`（原 `hwt_imu.c:81`），
     即只取 Roll/Pitch/Yaw。而 HWT906 是「三轴陀螺仪 + 三轴加速度计 +
     三轴磁力计」的九轴 AHRS，寄存器 0x34~0x40 里还有加速度、角速度、
     磁场、温度，全部没读。文件头当时甚至写着「这类模块对外只给
     roll/pitch/yaw，没有原始角速度/加速度」—— 这条注释是错的，本次一并修正。

  2. **寄存器表核对。** 仓库内 `obsolete/wit_protocol/wit_protocol.h:61-73` 就是
     维特官方 SDK 的寄存器索引表，与公开数据手册（WT901 / BWT901 / WT9011DCL
     等系列共用同一套协议）完全一致：

     | 地址 | 内容 | 换算 |
     |---|---|---|
     | 0x34 / 0x35 / 0x36 | AX / AY / AZ 加速度 | `raw / 32768 × 量程(g)` |
     | 0x37 / 0x38 / 0x39 | GX / GY / GZ 角速度 | `raw / 32768 × 量程(°/s)` |
     | 0x3A / 0x3B / 0x3C | HX / HY / HZ 磁场 | 原始值（mG，手册未给缩放系数） |
     | 0x3D / 0x3E / 0x3F | Roll / Pitch / Yaw | `raw / 32768 × 180` |
     | 0x40 | TEMP | `raw / 100` ℃ |

     **【寻址方式 —— 别再踩这个坑】** 维特 I2C 的寄存器地址是**索引**，与串口 /
     Modbus 协议的编号一致（0x34=AX … 0x40=TEMP），**每个索引占 2 字节小端**，
     不是「每个寄存器只占 1 个地址」。所以改动前「从 0x3D 读 6 字节」正好是
     Roll/Pitch/Yaw 三个寄存器，`hwt_imu.h` 里的 `0x3D/0x3E/0x3F` 三个宏是
     **对的**，与 `hwt_imu.c` 的 `buf[0..1]/[2..3]/[4..5]` 解析自洽 ——
     此前两代实现（`obsolete/hwt101_legacy/HWT101_iic.c` 的 `WitReadReg(Roll, 3U)`）
     也都按这个约定走。
     调研期间曾出现过「角度其实在 0x46、0x3D 读到的其实是角速度」的判断，
     那是把「索引」误当成了「字节地址」（按字节步进则 0x34+3×6=0x46），
     **是错的，不要据此改动**。

  3. **块读：一次事务把 0x34~0x40 全读回来。**
     `HWT_IMU_Poll()` 改为一次 `HAL_I2C_Mem_Read(..., HWT_IMU_REG_AX, ...,
     26 字节)`（13 个寄存器）。块内偏移由寄存器宏相减算出，不写硬编码数字
     （规范第 7.3 节），取数走统一的 `hwt_imu_block_i16(reg)`，姿态角与扩展量
     共用同一个取数口。新增 `hardware/sensors/hwt_imu.c` 的 `static uint8_t
     s_raw[26]` 放缓存 —— 用 static 而非局部数组，不占调用者的任务栈。

  4. **退化回退（本次改动的保险丝）。** 长块读失败时**自动退化**为
     原有那条已验证的路径：从 0x3D 读 6 字节到
     `&s_raw[HWT_IMU_BLOCK_OFF_ANGLE]`（偏移 18），并置 `g_hwt_imu_ext_ok = 0`。
     两条路径的姿态角解析偏移完全一致，无需分支。
     这样即使模块不接受 26 字节的长块读，**航向也不会跟着一起失效**，
     只是拿不到加速度那几个量 —— 照 V1.10.0 `SCS_BusInit()` 优雅失败的做法。
     两条都失败才置 `g_hwt_imu_online = 0` 并返回 0，语义与改动前完全一致。

  5. **量程做成宏，附台架核对方法。** 加速度 / 角速度的量程可在模块里改
     （加速度 ±2/4/8/16g，角速度 ±250/500/1000/2000°/s），换算系数随之变化。
     新增 `HWT_IMU_ACC_RANGE_G` / `HWT_IMU_GYRO_RANGE_DPS` 两个宏（默认 16g /
     2000°/s），换量程时只改这两处。
     **核对方法**：静止时三轴合矢量 `sqrt(ax²+ay²+az²)` 应约为 **9.8 m/s²**；
     若读到 78.4 / 39.2 / 19.6，说明实际量程是 ±2 / ±4 / ±8g，
     把 `HWT_IMU_ACC_RANGE_G` 相应改成 2.0 / 4.0 / 8.0。

  6. **`PoseData_t` 末尾追加三轴线加速度**（`device/pose_data.h`）：
     `float ax / ay / az`，单位 m/s²，传感器本体坐标系。
     依据规范第 3 节第 3 条「新增字段只能追加到末尾，保证前向兼容」，
     **未改动任何既有字段的顺序与类型**，结构体 40 B → 52 B。
     落地前已确认全工程对 `PoseData_t` **零** `sizeof` / `memcpy` / `memcmp` /
     数组化使用（三处 `*pose_out = s_pose` 是整体赋值），追加安全。
     只有 `imu_hwt906` 会填这三个字段；`locator_wheel` / `locator_ops9`
     没有加速度数据源，恒为 0（同 `vx/vy` 先例）。

  7. **`wz` 数据源改为陀螺仪 GZ 直接读取（本次唯一的行为变更）。**
     `device/HWT906.c` 此前用「yaw 差分 + wrap±π + 实测 dt」推算 `wz`
     （依据是驱动层没有原始角速度 —— 那个前提本次被推翻）。现改为
     `s_pose.wz = g_hwt_imu_gyro_z_rad * HWT906_GZ_SIGN`，
     相关的 `hwt906_wrap_pi()` 与 `s_prev_yaw_rad` / `s_prev_tick` /
     `s_have_prev` 三个差分状态一并删除（留着会触发 `-Wunused-function`）。
     陀螺仪给的是真实角速度，不受 yaw 更新率与量化限制。
     新增符号宏 `HWT906_GZ_SIGN`（默认 +1），附台架判据：
     **手转车身使 yaw 增大时 gz 必须同为正；若反号则改成 -1**
     —— 符号搞反等于角度环正反馈，会直接发散。
     退化路径（`ext_ok == 0`，无陀螺仪数据）下 `wz` 与 `ax/ay/az` **一律置 0**，
     绝不把上一拍的陈旧值当新数据发出去。

  8. **磁场与温度不进 `PoseData_t`。** 两者只在驱动层全局量
     （`g_hwt_imu_mag_x/y/z` / `g_hwt_imu_temp`）里，需要就直接读
     `hwt_imu.h`。理由：磁场/温度不是位姿数据，塞进所有定位源都要实现的
     公共契约结构里会污染契约；而 `PoseData_t` 只有加速度是真正与运动学
     相关的量（与既有的 `vx/vy/wz` 同族）。

  9. **不读四元数（0x50~0x54）。** 地址存在冲突：仓库内维特官方 SDK 头
     `obsolete/wit_protocol/wit_protocol.h:89-92` 写 `q0 = 0x50`、`q1 = 0x51`，
     而公开数据手册（WT9011DCL）写四元数从 **0x51** 起、返回包里就是 `0x51`。
     未实机确证前不臆造。且四元数与已有的 roll/pitch/yaw 是同一信息的两种
     表示，对当前工程（只要航向）无增量价值。

  10. **修正两处过时注释。** `hwt_imu.h` 文件头原写「没有原始角速度/加速度」
     与「本工程 I2C3 没有配置 DMA 通道」—— 后者是错的：
     `Core/Src/i2c.c:137` 的 `__HAL_LINKDMA(i2cHandle, hdmarx, hdma_i2c3_rx)`
     已把 I2C3 的 RX DMA 通道配好并链接，只是本驱动没有使用它（26 字节量级
     DMA 收益不明显，却要额外引入传输完成同步）。

- **备注**：

  1. **【临时调试脚手架，用完必须删】** `Core/Src/app_freertos.c` 的
     `StartDefaultTask()`（`defaultTask`）里加了一段
     `imu_hwt906.init/update/get_pose` + 九轴 printf，**每 10 圈打一行**
     （约 4~5Hz，不限流会把串口刷到没法看）。
     原因见下一条 —— IMU 在运行时**根本没有被轮询过**，不接这个观察入口
     就完全看不到数据。
     **这段与 `defaultTask` 的调度器职责无关，回退时整段删掉即可**
     （连同 `#include "HWT906.h"` / `#include "hwt_imu.h"` 两行）。

     **为什么最终放在 `defaultTask` 而不是 `ops9imu_task`**（开发中改过一次）：
     printf 走 `Core/Src/syscalls.c:96` 的 `_write` → `Core/Src/main.c:187` 的
     `__io_putchar`，而后者是**逐字节阻塞**的 `HAL_UART_Transmit(&huart2, ..., 1000)`
     —— 一次 printf 会变成上百次独立的单字节传输调用。
     huart2 为 115200 / 8N1，一行约 110 字符 ≈ **11ms 的纯线上时间**，
     比 `ops9imu_task` 的 10ms 周期还长；而那个任务是 `osPriorityHigh`，
     一阻塞会连它自己的 OPS9 串口排空一起卡住，让 `locator_ops9` 掉帧。
     `defaultTask` 是 `osPriorityNormal` 的空转循环（原循环体全被注释掉），
     会被 OPS9 抢占，且栈本来就是 `512 * 4` = 2KB、**不需要任何栈调整** ——
     把「顺手改任务栈」这个本来要写进变更记录的风险项整个消掉了。
  2. **【既有隐患，本次未动】`FC_Task` 全工程从未被创建。**
     `imu_hwt906` 的唯一引用点是 `app/worker_task.c:78,89,90` 的 `FC_Task`，

     三个线程（`:179,182,185`），`FC_Task` / `NLF_Task` 既未被 `osThreadNew`
     创建也未被调用（`fcTaskHandle` / `nlfTaskHandle` 定义了但永远为 NULL）。
     **也就是说 IMU 驱动在 V1.11.0 之前一直没进 `.elf`、运行时也没被轮询过**，
     `app/NavigationMecanum.c` 依赖的 `g_hwt_imu_yaw` 刷新链同样是悬空的。
     本工程自己的记录可作旁证：`clauderecord/2026-09-18.md:98` 写「`.elf` 内无
     `imu_hwt906`——未被引用被 `--gc-sections` 回收」，`:115` 复述「但 `.elf` 内
     仍无 `imu_hwt906` / `FC_Task`」，`:120` 写「待补任务创建后……

- **修改内容**：

  1. **需求与几何。** 要让小车跑圆弧且**车头方向恒为该圆弧的切线**：

     ```
     θ(t) = θ₀ + s/R          切向角 = 航向(车头方向)
     v    = ds/dt             线速度
     ω    = dθ/dt = v/R       ← 角速度与线速度锁定成比例
     ```

     即只要同时给底盘 `(v, ω = v/R)` 且车头已对准 θ₀，车自然画出半径 R 的弧。
     麦轮的 `Mecanum_Calc(float v, float w)`（`algorithm/mecanum.h:41`，
     注释写明 w 逆时针为正）**正好就是这个模型，无需任何新的运动学**。

  2. **根因：两条现成的路各缺一半。**
     - `algorithm/Circle_base.c:112` 用 `Mecanum_Calc_Full(vx, vy, 0.0f)` ——
       **w 恒为 0**，车只平移不转，车头方向固定，永远不可能是切线；
     - `app/worker_task.c` 的 FC_TASK 用 `Mecanum_Calc(0.0f, s_fc.cmd_w)` ——
       **线速度硬编码为 0**，只能原地转向，走不出弧。

     本次把 FC_TASK 那一半补齐（`Circle_base.c` 那半**刻意不动** ——
     它是另一条控制律，改动会波及既有找圆行为）。

  3. **契约扩展（追加，不动已有两条）。** `app/worker_task.h` 在既有的
     `g_angle_ctrl_enable` / `g_angle_target_yaw` 之后追加：

     ```c
     extern volatile float g_angle_ctrl_speed;   /* 目标线速度 m/s, >0 前进 */
     extern volatile float g_angle_ctrl_w_ff;    /* 前馈角速度 rad/s, CCW 为正 */
     ```

     依据规范第 5.3 节「优先扩展接口，不删除原有接口」。**两者默认全 0**，
     因此不设置它们时 FC_TASK 的行为与 V1.12.0 **逐位等价**（纯原地转向）。
     定义处仍在 `app/worker_task.c`，与既有两条同处，保持"唯一定义处"。

  4. **FC_TASK 一行改动**（`app/worker_task.c`）：


  5. **【关键设计】前馈加在内环*输出*，不是加在 PID 目标上。**
     `algorithm/angle_ctrl.c:77` 有 `ac->gyro_scale = 0.05f;` —— 内环的反馈量
     `w_filt` 被乘了 **0.05**，速度环只"看到"5% 的真实角速度，**它不是真正的
     速度环**，只是弱比例项；叠加 V1.11.0 把 `wz` 从 yaw 差分换成陀螺仪后
     没重新整定（记录里已标未验证，见本文件 V1.11.0 第 7 条）。

     前馈若加在 `target_w` 上会被这个缩放揉坏；加在输出上则几何量直通、
     PID 管不着，只在此基础上修残差。
     **取舍已与用户确认**：本次刻意**不动内环整定**，把它留作后续独立一项
     （它本来就在 V1.11.0 的未验证清单里）。副作用是 `g_angle_ctrl_w_ff`
     **不受 `angle_ctrl.c` 的 `CFG_MAX_W` 限幅约束** —— 由调用方保证量程，
     `arc_path` 用 `ARC_W_MAX` 做这道校验。

  6. **【关键设计】不需要新增"跟踪模式"标志。**
     `angle_ctrl.c:108-111` 有个"转到位就停"的闩锁：
     `yaw_err < yaw_tol`（1°）时置 `ANGLE_ARRIVED` 并把 `cmd_w` 清零。
     乍看会让弧上运动"打嗝"，但把 `w_ff` 放在**输出端**之后，它退化成
     **PID 项的 ±1° 死区**：`w_ff` 照常输出、车不停转，误差超过 1° 时
     PID 才介入。这个死区对圆弧跟踪是**有益**的（抑制小误差抖动），
     且 `Angle_UpdateTarget()` 每拍会把 `state` 复位成 `MOVING`，不会永久闩死。
     **故不加状态量。**

  7. **新增 `algorithm/arc_path.c` / `.h`**（业务层，与 `Circle_base.c` 同层）：

     ```c
     #define ARC_W_MAX   3.0f    /* rad/s, 与 angle_ctrl.c 的 CFG_MAX_W 一致 */
     void Arc_SetParam(float radius_m, float v_mps, float sweep_deg);
     bool Arc_Run(void);         /* 阻塞式, 与 Nav_MoveBody 同风格 */
     void Arc_Abort(void);
     ```

     `Arc_Run()` 要点：

     - **参数校验优先**：`R`/`v`/`sweep` 任一为 0，或 `|v/R| > ARC_W_MAX`
       （几何上实现不了），**直接返回 false 不驱动电机**；
     - **IMU 健康检查**：先等 `imu_hwt906.is_healthy()`（最多 `ARC_IMU_WAIT_MS`
       = 200ms，FC_TASK 每 10ms 刷新一次）。航向不可信时**绝不盲开**；
     - **起始切向角** `θ₀ = g_hwt_imu_yaw`（车头当前朝向即圆弧起点切线）；
     - **★ 动目标每拍推进**（本模块最容易写错的一处）：
       `g_angle_target_yaw = θ₀ + w_deg * t`，`t` 由 `HAL_GetTick()` 反算而非
       自增计数（`osDelay` 的实际周期会被 `Send_commandmotor()` 内含的
       `osDelay(5)` 拉长，累加会漂）。
       **若只设一次 θ₀ 就不再更新，PID 会把车的正常圆弧运动当成航向误差去
       反向纠正，前馈与反馈互相打架** —— 车要么不转要么乱转；
     - **超时兜底**：按 `sweep/|w_deg|` 算所需时间，留 50% 余量再兜 1s，
       防止 FC_TASK 异常时死等（同 `Nav_MoveBody` 的 `guard` 思路）；

       发零速）并清掉速度/前馈，再 `osDelay(20)` 等零速真的发出去（契约要求）。
